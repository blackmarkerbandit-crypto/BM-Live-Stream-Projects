Section 1 — The question (1 item)

Item 1 — Can a viewer watch one specific episode on demand?

Status: OPEN QUESTION — needs a yes/no before we design around it.

QUESTION Does ChannelCast have any way to play a single media item to a viewer — a VOD mode on the embed, a hosted watch page, or an endpoint that returns a playable URL for a given mediaId? If it does not exist today, is it on the roadmap?

CONTEXT The BlackMarker.TV 3.0 homepage has a “Latest Videos” row: one card per show, each showing that show’s newest episode with its real poster and duration, pulled live from list_category_items. The obvious behaviour when someone clicks a card is “play this episode.” We could not build that.

EVIDENCE The embed player accepts exactly three options and requires a channel:

class Player {
  constructor(opts) {
    this.apiBase   = opts.apiBase || defaultApiBase();
    this.channelId = opts.channelId;
    if (!this.channelId) throw new Error("ChannelCastPlayer: channelId is required");
    this.host      = resolveTarget(opts.target);

The only options read anywhere in embed/player.js are apiBase, channelId and target. There is no mediaId path, and no VOD state — the player is a channel player: it watches /api/v1/playback/status and /api/v1/playback/timeseek and switches between live and the scheduled loop.

RULED OUT We checked for a hosted watch page before asking. Both return 404:

GET https://channelcast.tv/watch/019fbbd1-bdac-7b70-a80b-15b18e2495c6   404
GET https://channelcast.tv/media/019fbbd1-bdac-7b70-a80b-15b18e2495c6   404

We also confirmed list_media returns no playable URL — the fields are id, title, filename, status, durationSeconds, processing, posterUrl.

RULED OUT We could play the S3 object directly in a plain <video> tag — the bucket is publicly readable and we have the paths. We deliberately did not. It would bypass ChannelCast completely: no play recorded through /api/v1/playback/track, so those views would never appear in play_report; no lower-third overlay; no logo bug; and a hardcoded S3 path that breaks silently if a file is moved or re-encoded. Under-counting our own best content to save a click is a bad trade.

WHAT WE DID INSTEAD Each card links to that show’s page rather than to the episode. That is also the better product call on its own merits — a card that drops a viewer into hour two of a three-hour podcast is worse than one that lands them on the show, where they can see every episode and choose. So this is not urgent for us.

IMPACT Beyond this site: a broadcaster running a back catalogue on ChannelCast has no way to let a viewer watch a specific episode. Everything is “what is on the channel right now.” For a platform sold to other broadcasters, on-demand viewing of your own library seems like it belongs in the product rather than in each customer’s front end. Worth knowing whether that is a gap, a deliberate scope decision, or already planned.

NOT A BUG To be explicit: nothing here is broken and nothing is blocked. We have shipped around it. This is a question about where the capability should live.

Section 2 — What the 3.0 homepage now depends on (for your awareness)

Three sections of the homepage went live against real ChannelCast data this week. Recording the endpoints here so nothing surprises you if any of them change.

Homepage sectionSourceAuth
Now PlayingGET /api/v1/playback/timeseek/{channelId}None — called from the browser
Upcominglist_schedules + list_playlist_itemsMCP token, server-side only
Latest Videoslist_categories + list_category_items + list_mediaMCP token, server-side only

CONTEXT The MCP token can delete_media and delete_playlist, so it never goes near a browser. A generator runs server-side and writes a static JSON file holding only titles, schedule offsets and poster URLs. The page reads that plus the public timeseek feed, and cross-checks the two — if timeseek names a mediaId that is not where the stored schedule says it should be, the page trusts timeseek and flags that its generated data is stale.

EVIDENCE Useful confirmations from building it, in case they are worth documenting on your side:

  • timeseek serves Access-Control-Allow-Origin: *, which is what makes browser-side Now Playing possible at all. If that ever tightens, the homepage loses its live now-playing.
  • list_schedules returns 28 weekly entries with real startUtc values. We use these rather than assuming Eastern is UTC−4 — that assumption is correct today and would break at the November DST change.
  • list_category_items exposes sort, and sort 0 being the newest is what makes the “latest episode” cards correct. We rely on that ordering.
  • list_media’s search behaves as a SQL LIKE over the title. A multi-word phrase fails whenever punctuation sits between the words — three of six poster lookups came back empty until we switched to probing with single words. Worth a line in the docs.

QUESTION (minor) Is there a supported way to fetch a media record by mediaId directly? Today the only route to a poster is list_media with a search string that happens to match, which is indirect and a little fragile.
