Item 01 — The live stream doesn’t hold. The player drops back to the scheduled playlist mid-broadcast.

Priority: P1 – highest  |  Status: OPEN – needs to be built or fixed. This is a request.  |  Area: Live Player & Playback

What should happen: as long as an encoder is pushing a live signal, the player shows LIVE — full stop. When the signal genuinely ends, it falls back to the scheduled loop.

What actually happens: the player sometimes drops out of the live stream and back into the playlist while we are still live and still sending. Viewers who came for the show end up watching the 24/7 loop instead, and they have no way of knowing they’re in the wrong place. This is the single most damaging bug on the list for us — it burns the promotion for every live show it hits.

  • ACTION NEEDED: What we need: something that keeps checking for a live signal and holds the player on live for as long as ingest is alive — with a tolerance window for a brief network hiccup instead of an instant fallback. A two-second blip should not end the broadcast.
  • ACTION NEEDED: And the way back: when the signal recovers, the player should return to live on its own. Right now the assumption seems to be that a viewer will refresh — they won’t.
  • CONTEXT: Question for Jose: what actually triggers the switch back to the playlist? A fixed ingest timeout, a missed-keyframe / GOP threshold, a gap between segments, or a health check that fails on one bad response? Knowing which one it is tells us whether this is a threshold to loosen or a reconnect path that isn’t there.
  • SUGGESTION: Next time it happens we’ll grab the wall-clock time so it can be matched against the ingest logs. If there’s a stream-health log we can see on our side, point us at it.

Item 02 — A true grid layout for the single-category embed — rows & columns, plus copy-paste embed code.

Priority: P1 – highest  |  Status: OPEN – needs to be built or fixed. This is a request.  |  Area: Live Player & Playback

The single-category embed itself works — OTTRenderer.mount({ target, feedUrl, category, theme }) renders one category’s episodes with playback, and we use it on every show page. What’s missing is layout control. Every embed comes out as a horizontal scrolling rail, and the dashboard’s row|grid toggle has no effect on it.

The ask, plainly: give us a real grid where we can set rows and columns, and a copy-paste embed snippet from the dashboard with those options already baked in — so we can delete the CSS workaround we’re running now. Everything below is the evidence for why it can’t be done today.

  • ACTION NEEDED: What we want, concretely: (1) grid layout with rows × columns we choose; (2) generated embed code from the dashboard for a single category, not just the whole catalog; (3) pagination or “load more” when the category has more items than rows × columns; (4) keep the theming we already have (bg, tile, text, accent).
  • ACTION NEEDED: Grid is unreachable today — traced in the renderer source (Jul 22, verified on screen). Eric flipped The Weekly Interrupt to type: "grid" in the dashboard; the embed still rendered a horizontal rail. Why: (a) options.category passed to mount() is only a feed filter — it trims data.items and nothing more. (b) state.activeCategory initialises to "" and is only assigned inside the category-bar click handler. (c) Layout is decided by verticalBrowseMode = Boolean(state.activeCategory) — therefore false on first render, always. (d) The renderer never reads a layout/type field from the feed, so the dashboard’s row|grid flag has zero effect on an embed. (e) mount() returns nothing (window.OTTRenderer = { mount }, no instance), so we can’t set the view programmatically either. The grid CSS already exists (.ott-track-vertical → repeat(auto-fill,minmax(220px,1fr))) — it’s just unreachable on load.
  • ACTION NEEDED: Jose — smallest possible fix (pick one): (1) One-liner: when options.category is supplied, also seed state.activeCategory = options.category. (2) Explicit: add a layout: 'row' | 'grid' option to mount(). (3) Data-driven: read the category’s type from the feed and honour grid — what Eric expected the dashboard toggle to do. Our preference: (2) + (3) — an explicit override with the dashboard flag as the default. Please also make mount() return an instance so embeds can drive the view.
  • CONTEXT: Why our workaround isn’t good enough. We force ChannelCast’s own .ott-track-vertical class on ourselves, which collides with the renderer’s horizontal virtualization: renderWindow() derives its window from track.scrollLeft and track.clientWidth (visibleCount = ceil(clientWidth / step) + HORIZONTAL_OVERSCAN*2, overscan 3). Vertical track ⇒ scrollLeft is permanently 0 ⇒ it renders one window of ~10–12 cards and never advances. Net: Can You Dig It!? has 22 episodes and the page can only ever show about 12 — the rest are unreachable by any amount of scrolling.
  • ACTION NEEDED: Eric’s test. Is there a copy-paste option in the dashboard to grab a single-category embed (e.g. just Can You Dig It!?) rather than only the whole catalog?
  • SUGGESTION: Nothing wrong with the rail for a homepage “rows of shows” layout — this is specifically about a single-category archive page, which is the main reason to use the per-category embed at all.

Item 03 — MRSS feed throws away the curated episode order and stamps every item with the same date.

Priority: P1 – highest  |  Status: OPEN – needs to be built or fixed. This is a request.  |  Area: 3.0 Site — Data & Embeds

Episodes come out of the feed in a seemingly random order on every show page. Two separate causes, both in the feed: (1) the feed ignores the category's sort field entirely and emits items in descending alphabetical order by title; (2) every single item carries an identical pubDate — Fri, 03 Jul 2026 05:42:58 GMT, the bulk-import timestamp — so nothing downstream can fall back to sorting by date either.

  • CONTEXT: Concrete example (Can You Dig It!?): in the backend the newest episode “Back from the NYC 2026 Weekend — 06-26-2026” is correctly sort 0. In the feed it lands at position 17 of 21, because “B” sorts late in a descending A–Z list. The feed order runs Traxx → Tito → The Leftovers → Tampa Tony → … → Annex → 2Turnt. That's alphabetical, not chronological.
  • CONTEXT: So the ordering is right in ChannelCast — the sort values are clean and newest-first. It's purely the feed that drops them.
  • ACTION NEEDED: What we need: the feed should emit items in the category's sort order (and ideally expose sort as a field so consumers can re-sort). Separately, give each item a real pubDate — original episode/air date if you have it, upload date otherwise — so date sorting works at all.
  • SUGGESTION: This also decides which episode shows up as the big featured/hero tile at the top of each show page, so right now the hero is effectively chosen alphabetically rather than “latest episode”.

The raw play log records the same video multiple times in a tight cluster. This inflates every play count we show a client — the broadcast numbers that are working, and now the VOD numbers too.

(b) Server (safety net): dedupe on ingest — collapse identical (mediaId + session/IP) events inside a short window — so stray duplicates never reach a client’s numbers.
